## BUG-01 (Crítico / P0): Divergência de Setting de RLS nas Migrations 0028 e 0029

### 📍 Arquivos Afetados
- `backend/alembic/versions/0028_supplies_and_inventory.py` (linhas 142, 145, 157, 160)
- `backend/alembic/versions/0029_procedure_supplies.py` (linhas 82, 85)

### 💥 Descrição do Problema e Impacto
As migrations de criação de tabelas de estoque e insumos definiram as policies de Row-Level Security (RLS) referenciando o parâmetro de sessão `app.current_professional_id`.
No entanto, o backend da aplicação (`app/db/session.py`) define `app.professional_id` em todas as conexões transacionais.

Como `app.current_professional_id` nunca é populado pelo backend, a RLS do PostgreSQL avalia a policy como `NULL`, bloqueando **qualquer operação de INSERT, UPDATE ou SELECT** nas tabelas:
- `supplies`
- `supply_movements`
- `procedure_supplies`

Isso faz com que o endpoint `POST /api/v1/supplies` estoure o erro:
```text
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.InsufficientPrivilege) new row violates row-level security policy for table "supplies"
```
E falha o teste arquitetural:
```text
FAILED tests/test_architecture.py::test_toda_tabela_com_professional_id_tem_rls_nas_migrations
```

### 🛠️ Solução Recomendada
Substituir todas as ocorrências de `app.current_professional_id` por `app.professional_id`:

#### 1. Em `backend/alembic/versions/0028_supplies_and_inventory.py`:
```sql
-- ONDE ESTÁ:
professional_id = NULLIF(current_setting('app.current_professional_id', true), '')::uuid

-- DEVE FICAR:
professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid
```
*(Fazer a substituição para as duas policies: em `supplies` e em `supply_movements`)*

#### 2. Em `backend/alembic/versions/0029_procedure_supplies.py`:
```sql
-- ONDE ESTÁ:
professional_id = NULLIF(current_setting('app.current_professional_id', true), '')::uuid

-- DEVE FICAR:
professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid
```

#### 3. No Banco Local / Supabase:
Se as migrações já tiverem sido aplicadas, criar uma migration `0030_fix_supplies_rls_setting.py` ou executar o ALTER POLICY para corrigir as policies ativas no PostgreSQL:
```sql
ALTER POLICY tenant_isolation ON supplies
  USING (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid)
  WITH CHECK (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid);

ALTER POLICY tenant_isolation ON supply_movements
  USING (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid)
  WITH CHECK (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid);

ALTER POLICY tenant_isolation ON procedure_supplies
  USING (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid)
  WITH CHECK (professional_id = NULLIF(current_setting('app.professional_id', true), '')::uuid);
```

## BUG-02 (Crítico / P0): Prefixo Duplicado `/v1/` no Client de API do Frontend

### 📍 Arquivos Afetados
- `frontend/src/features/supplies/suppliesApi.ts`
- `frontend/src/features/vials/vialsApi.ts`
- `frontend/src/features/whatsapp-campaigns/campaignsApi.ts`

### 💥 Descrição do Problema e Impacto
O cliente HTTP do frontend (`src/lib/http/client.ts`) concatena `${BASE}${cleanPath}`, onde `BASE` é `/api/v1` (ou `http://localhost:8000/api/v1`).
A função `cleanPath` remove apenas strings que começam explicitamente com `/api/v1`.

Como esses 3 arquivos usaram caminhos iniciando com `/v1/...`:
- `api.get("/v1/supplies")` ➔ chama `/api/v1/v1/supplies` (**404 Not Found**)
- `api.get("/v1/vials")` ➔ chama `/api/v1/v1/vials` (**404 Not Found**)
- `api.get("/v1/patients/birthdays")` ➔ chama `/api/v1/v1/patients/birthdays` (**404 Not Found**)

Isso quebra **100%** do carregamento e submissão de formulários das telas de Estoque, Frascos de Botox e Aniversariantes do Mês.

### 🛠️ Solução Recomendada

#### 1. Em `frontend/src/features/supplies/suppliesApi.ts`:
Remover o `/v1` inicial de todas as chamadas `api.*`:
- Linha 80: `/v1/supplies` ➔ `/supplies`
- Linha 84: `"/v1/supplies"` ➔ `"/supplies"`
- Linha 91: `/v1/supplies/${supplyId}` ➔ `/supplies/${supplyId}`
- Linha 95: `/v1/supplies/${supplyId}` ➔ `/supplies/${supplyId}`
- Linha 102: `/v1/supplies/${supplyId}/movements` ➔ `/supplies/${supplyId}/movements`
- Linha 106: `/v1/supplies/${supplyId}/movements` ➔ `/supplies/${supplyId}/movements`
- Linha 110: `"/v1/supplies/movements/recent"` ➔ `"/supplies/movements/recent"`

#### 2. Em `frontend/src/features/vials/vialsApi.ts`:
- Linha 43: `"/v1/vials"` ➔ `"/vials"`
- Linha 47: `"/v1/vials?include_all=true"` ➔ `"/vials?include_all=true"`
- Linha 51: `"/v1/vials"` ➔ `"/vials"`
- Linha 55: `/v1/vials/${vialId}/consume` ➔ `/vials/${vialId}/consume`
- Linha 59: `/v1/vials/${vialId}/finish` ➔ `/vials/${vialId}/finish`
- Linha 63: `/v1/vials/${vialId}` ➔ `/vials/${vialId}`

#### 3. Em `frontend/src/features/whatsapp-campaigns/campaignsApi.ts`:
- Linha 18: `/v1/patients/birthdays${query}` ➔ `/patients/birthdays${query}`

*(Opcional / Defensivo)*: Em `frontend/src/lib/http/client.ts`, linha 36, proteger o sanitizador de path com regex mais flexível:
```ts
const cleanPath = path.replace(/^\/(?:api\/)?v1/, "");
```

## BUG-03 (Alto / P1): Chamadas Explícitas a `self._session.commit()` no `SupplyService`

### 📍 Arquivo Afetado
- `backend/app/services/supply_service.py` (linhas 74, 101, 108, 141)

### 💥 Descrição do Problema e Impacto
A injeção de dependência `DbSession` no FastAPI (`app/api/deps.py`) utiliza `get_tenant_session`, que gerencia o ciclo da transação via context manager:
```python
with session.begin():
    _set_tenant(session, professional_id)
    yield session
```
No SQLAlchemy 2.0, chamar `session.commit()` manualmente dentro de um bloco `with session.begin():` fecha a transação antes do término do bloco. Qualquer instrução posterior (como `self._session.refresh(...)` ou listeners de pós-execução do FastAPI) gera:
```text
sqlalchemy.exc.InvalidRequestError: Can't operate on closed transaction inside context manager. Please complete the context manager before emitting further commands.
```

### 🛠️ Solução Recomendada
Em `backend/app/services/supply_service.py`, substituir `self._session.commit()` por `self._session.flush()`:
- **Linha 74:** trocar `self._session.commit()` por `self._session.flush()`
- **Linha 101:** trocar `self._session.commit()` por `self._session.flush()`
- **Linha 108:** trocar `self._session.commit()` por `self._session.flush()`
- **Linha 141:** trocar `self._session.commit()` por `self._session.flush()`

O commit final deve ser delegado exclusivamente ao context manager `with session.begin():` de `get_tenant_session`.

## BUG-04 (Alto / P1): Fallback de Slug Público com Risco de Vazamento Multi-Tenant

### 📍 Arquivo Afetado
- `backend/app/api/v1/public_agenda.py` (linhas 100 a 125)

### 💥 Descrição do Problema e Impacto
Na resolução de links públicos de auto-agendamento (`/agendar/:slug`):
```python
if not row and clean_slug in ("minha-agenda", "agenda", "default"):
    fallback_stmt = select(...).order_by(Professional.id.asc())
    fallback_row = sys_sess.execute(fallback_stmt).first()
```
Se qualquer paciente ou usuário acessar uma URL com slug genérico como `/agendar/minha-agenda` ou `/agendar/default`, o sistema seleciona silenciosamente o **primeiro profissional cadastrado no banco de dados** (`Professional.id.asc()`).

Em um ambiente SaaS real de produção multi-clínica, pacientes de outros profissionais/clínicas terão seus agendamentos atribuídos indevidamente a um terceiro.

### 🛠️ Solução Recomendada
Remover o fallback hardcoded para produção. Se o slug não existir exatamente, deve retornar `404 Not Found`:

```python
# backend/app/api/v1/public_agenda.py
def _resolve_slug(slug: str) -> tuple[UUID, str, str | None, str, str | None, str | None]:
    clean_slug = slug.strip().lower()
    with unsafe_session_without_tenant("lookup public agenda slug") as sys_sess:
        stmt = select(
            Professional.id,
            Professional.name,
            Professional.bio,
            Professional.slug,
            Professional.avatar_url,
            Professional.specialty,
        ).where(
            Professional.slug == clean_slug,
            Professional.is_active.is_(True),
        )
        row = sys_sess.execute(stmt).first()

        if not row:
            raise HTTPException(
                status_code=status.HTTP_404_NOT_FOUND,
                detail="Agenda não encontrada para este link.",
            )
        return row[0], row[1], row[2], row[3] or clean_slug, row[4], row[5]
```

## BUG-05 (Médio / P2): Testes de Domínio Mascarados por `MagicMock`

### 📍 Arquivos Afetados
- `backend/tests/test_supplies.py`
- `backend/tests/test_procedure_supplies.py`

### 💥 Descrição do Problema e Impacto
Ambos os arquivos utilizam `MagicMock` para a sessão do SQLAlchemy (`mock_session = MagicMock()`) e repositórios. Isso fez com que:
1. O teste validasse explicitamente `mock_session.commit.assert_called_once()`, consolidando o BUG-03 como "comportamento esperado".
2. Os testes nunca executassem queries reais contra o PostgreSQL, fazendo com que o BUG-01 (erro de sintaxe na policy de RLS) passasse 100% despercebido nos testes.

### 🛠️ Solução Recomendada
Refatorar os testes para utilizar o padrão de testes de integração com `TestClient` e banco de dados real em transação com rollback (mesmo padrão adotado em `test_vials.py` e `test_sales_integration.py`):
- Testar a criação real de insumo via `POST /api/v1/supplies`.
- Testar a baixa automática de estoque na conclusão de atendimento via `PATCH /api/v1/sessions/{id}` com status `COMPLETED`.

## BUG-06 (Baixo / P3): Inconsistência de Formatação de Moeda no Agendamento Público

### 📍 Arquivos Afetados
- `frontend/src/features/public-booking/PublicBookingPage.tsx` (linhas 292, 391, 428)
- `frontend/src/features/public-booking/BookingManagementPage.tsx` (linha 237)

### 💥 Descrição do Problema e Impacto
Nesses componentes, o preço do procedimento foi formatado manualmente com:
```tsx
`R$ ${parseFloat(selectedProcedure.price).toFixed(2).replace(".", ",")}`
```
Isso viola a diretriz de engenharia (Invariante I1) e causa dois problemas:
1. Para valores acima de R$ 999,99, o `.replace(".", ",")` gera `R$ 1500,00` em vez de `R$ 1.500,00` (sem separador de milhar).
2. Converte strings decimais exatas em float64 (`parseFloat`).

### 🛠️ Solução Recomendada
Importar e utilizar os formatadores padronizados de `src/lib/money/`:
```tsx
import { formatBRL } from "@/lib/money/format";
import { money } from "@/lib/money/money";

// No lugar do parseFloat:
formatBRL(money(selectedProcedure.price))
```
